# PLAN — Settle v2: from habit logger to a self-hosted transaction intelligence platform

Replaces the previous plan (theme toggle + Patterns charts). Its steps 1–4 are done; its step 5 (browser proof + Codex gate) is carried into M0 as step 0.5.

## Goal
Rescope Settle from a playful spend logger with play money into a finance-grade, self-hostable product that one person (scaling to ~10 invited users) uses on their real statements. The engineering story for recruiters: an event-driven ingestion pipeline, merchant entity resolution, statistical subscription and anomaly detection, a probabilistic cash-flow forecast, all posted to the existing double-entry ledger, with bank-style security and privacy controls and a calm, dense, keyboard-first UI.

**Task routing:** DESIGN/VISUAL + ambiguous → full treatment (look-checks at UI milestones). Some steps are SPEC-COMPLETE (marked `[spec]`); those get tests written first and lean dispatch.

**Delivery:** one PR per milestone, branched from `main` after the current branch merges. Never one giant PR.

---

## Product thesis (the business idea)

**Settle: open-source transaction intelligence you run yourself.**

Every bank, card issuer, expense-management tool (Ramp, Brex, Expensify) and accounting product runs the same back office:
**ingest messy statements → reconcile → resolve merchants → classify → detect recurring charges and anomalies → forecast cash risk.**
Vendors sell this as an API (Plaid Enrich, Ntropy, MX, Spade). Settle runs it for one household, self-hosted, on the user's own keys, with a real double-entry ledger as the system of record.

Why this framing stands out:
- It's a **data platform problem**: messy inputs, idempotent pipelines, lineage, data quality. It's not a dashboard over an API.
- It's a **risk problem**: anomaly reason codes, forecast uncertainty, probability of overdraft. These are risk-analyst tools, not "spent $X on coffee".
- It's a **security and privacy problem**: the data is personal financial records, so encryption, tenancy isolation, audit and deletion are first-class.
- The scale is honest: ~10 users on free tiers. Scale readiness is shown with idempotency, partitioning, load tests and back-pressure, not with spend.

Model: like Actual Budget or Firefly III (self-host, BYO keys), but the enrichment, risk and forecasting layers are the difference.

**Non-goals:** moving real money; investment advice; a stock bot; public sign-up; storing full card or account numbers (last 4 only).

### Resume bullets this plan is built to earn (fill in the measured numbers at the end)
- Built an event-driven statement ingestion pipeline (S3 → SQS → worker → Postgres double-entry ledger) with idempotent posting, cross-statement de-duplication, a DLQ and replay, and data-quality gates. Processed N months of real statements with zero double-posted rows.
- Wrote a merchant entity-resolution layer (descriptor cleaning + trigram fuzzy match + confidence scoring + rules learned from corrections). Reached X% top-1 precision on a labeled set of N descriptors.
- Ported a recurring-charge detector to a tested backend service and added a Monte Carlo cash-flow forecast with P10–P90 bands, backtested at Y% interval coverage.
- Hardened a fintech app with TOTP MFA, Postgres row-level security, per-user envelope encryption (KMS) with crypto-shredding on deletion, an append-only audit log and a STRIDE threat model.

## M2 — Identity, security and privacy  (PRs 3–4)

2.1 `[spec]` **Session hardening.** Rotate the session id on login and privilege change; idle timeout (30 min) plus absolute timeout (7 days); `__Host-` cookie, `Secure`, `HttpOnly`, `SameSite=Lax`; Origin/`Sec-Fetch-Site` check on every mutating route (CSRF); sessions table with device, IP prefix and last-seen. DONE WHEN: tests for rotation, both timeouts, a cross-origin POST rejected, and revoking one session from another.
2.2 `[spec]` **TOTP MFA + recovery codes** (RFC 6238, `node:crypto`, no new dependency). The secret is encrypted at rest; 10 single-use recovery codes stored as scrypt hashes; step-up for sensitive actions (export, delete, key changes). DONE WHEN: RFC 6238 test vectors pass; tests for replayed code, clock skew ±1 step, recovery-code single use.
2.2b **Passkeys (WebAuthn) as a second factor or passwordless sign-in.** Phishing-resistant, the bank-grade option. Verification by hand with `node:crypto` (ES256 + RS256, CBOR attestation `none`), or `@simplewebauthn/server` if approved under the DEPENDENCY GATE. Sign-in order: passkey → password + TOTP → recovery code. DONE WHEN: tests with recorded authenticator fixtures for registration, assertion, a sign-count regression rejected, and a wrong origin rejected.
2.3 `[spec]` **Login abuse controls.** Per-account and per-IP backoff, generic error messages, no user enumeration on sign-up/reset, breached-password check via HIBP k-anonymity range API (only the first 5 hash chars leave the server). DONE WHEN: tests for lockout curve and identical responses for known and unknown emails.
2.3b `[spec]` **Database TLS verification.** `auth.ts` (and the 0.4 rate-limit store) connect with `ssl: { rejectUnauthorized: false }`, which accepts any certificate and allows a man-in-the-middle on the database link. Pin the Supabase CA (`sslrootcert`, shipped in the repo) and verify the full chain. DONE WHEN: a connection to a server with a self-signed cert fails in a test; the real connection still works.
2.4 `[spec]` **Tenant isolation in the database.** Postgres row-level security on every per-user table (`spend_logs`, `money_profiles`, imports, transactions, rules, sessions); the BFF sets `app.user_id` per transaction through a non-owner role. DONE WHEN: an integration test proves user A cannot read B's rows even with a hand-written query through the app role.
2.5 **Envelope encryption + crypto-shredding.** A per-user data key (AES-256-GCM via `node:crypto`) encrypts sensitive columns (raw descriptors, notes, account last4, uploaded files); the data key is wrapped by a KEK in AWS KMS (or Azure Key Vault, see Decisions), with a local KEK in dev and practice. Deleting an account destroys its wrapped key, so backups become unreadable for that user. DONE WHEN: tests for round-trip, wrong-tenant decryption failure, and that a shredded user's ciphertext cannot be decrypted.
2.5b **Encryption model, written down (answers "advanced encryption, or a compiler?").** Obfuscating or compiling code adds no security: anything shipped to a browser can be read. The protection is in where keys live and who can use them. Layers: TLS 1.2+ in transit with HSTS (already set); Postgres/S3 encryption at rest (provider-managed); **application-level envelope encryption** of sensitive fields with per-user AES-256-GCM data keys wrapped by a KMS key that the database never sees, so a stolen database dump or backup is unreadable; HMAC-SHA256 blind indexes so encrypted descriptors can still be matched for dedupe without decrypting; key rotation (re-wrap data keys under a new KEK version without re-encrypting data) with a tested rotation command; scrypt password hashes (existing). Optional extra: **end-to-end encrypted export** (the user's passphrase → scrypt → AES-GCM, so the downloaded backup is useless without it). Full client-side E2E encryption of live data is a non-goal, because the server must compute dedupe, subscriptions and forecasts; ADR 0004 records that trade-off. DONE WHEN: `docs/SECURITY.md` encryption section plus tests for blind-index equality, KEK rotation and encrypted-export round-trip.
2.6 **Append-only security audit log** (login, MFA change, session revoke, export, delete, key change), shown in Settings → Security. Postgres trigger blocks UPDATE/DELETE, matching the ledger's `ledger_entries` pattern.
2.7 **Data rights.** Export everything (JSON + CSV, zipped); delete the account (step-up, 7-day grace, then crypto-shred); retention policy (raw upload files purged after N days once parsed).
2.8 **Secrets and BYO keys.** Users store their own LLM and logo-provider keys in Settings, encrypted with their data key, never returned to the browser after save (show last 4). Server-side env secrets audited; `.env.example` documents every key.
2.9 **Supply chain + CI security.** gitleaks, `npm audit --omit=dev` / OSV-Scanner, CodeQL (free on public repos), Dependabot, CycloneDX SBOM artifact, Trivy scan of the Java image. DONE WHEN: CI runs all of them green on the PR.
2.10 **Corporate paperwork, done properly for a solo operator.** Rewrite `Legal.tsx`: Privacy Policy (what's collected, why, retention, subprocessors list — Vercel, Render, Supabase, AWS, optional LLM/logo provider — user rights, contact, 18+ US-only as decided in HANDOFF), Terms of Use, "not financial advice" disclaimer, cookie notice (essential cookies only, so no banner), `/.well-known/security.txt`, `SECURITY.md` disclosure policy. Clearly labeled "template, not legal advice". The operator legal name is still pending from the user.

## M3 — Ingestion pipeline  (PRs 5–6) — the core of the rescope

3.1 `[spec]` **Canonical schema + data contract.** `schemas/transaction.v1.json` (JSON Schema) and migrations: `imports` (file hash, source, status, counts), `raw_rows` (immutable, file hash + line number), `transactions` (normalized: account, posted_date, amount_minor, currency, descriptor_raw (encrypted), descriptor_clean, merchant_id, category_id, dedupe_key, lineage ids, pipeline version). DONE WHEN: schema validation tests for valid and invalid rows; migration runs up and down.
3.2 `[spec]` **Importers.** Generic CSV with column mapping and saved bank presets; OFX/QFX; Bank of America credit-card PDF (port `convert_bofa_pdf.py`, keeping its section-total check and refusing partial output). Each importer is a pure function `file → rows + checks`. DONE WHEN: golden-file tests on synthetic fixtures (copy SubscriptionRadar's `data/sample`), including malformed files rejected with a specific reason.
3.3 `[spec]` **Dedupe across overlapping statements.** `dedupe_key = hash(account, posted_date, amount, descriptor_clean, occurrence_index_within_day)`, so two identical same-day coffees are kept and overlapping exports are not double-counted. DONE WHEN: the SubscriptionRadar fixture yields exactly 72 outflows and both identical coffees remain.
3.4 **Async pipeline.** Browser uploads to S3 through a presigned PUT (size and type limits, SSE-KMS) → S3 event → SQS → worker: parse → validate → stage → dedupe → post to the ledger with idempotency key `import-<fileHash>-<row>`. 3 retries with backoff, then DLQ; `settle replay <importId>` command. Practice mode runs the same stages in-process. DONE WHEN: integration test (LocalStack, or the in-process adapter) imports the same file twice and the ledger shows one posting per row; a poisoned row lands in the DLQ without blocking the rest.
3.5 **Import job status + progress UI.** `GET /imports/:id` returns stage-by-stage progress; the Imports page reuses the staged-steps component from 0.3 (Uploaded → Parsed 214 rows → 2 rejected → 12 duplicates skipped → Posted 200 → Enriched). Rejected rows are shown with a reason and can be fixed or ignored.
3.6 **Data-quality gates per import.** Row count vs statement, section totals, balance continuity across consecutive statements (closing balance N = opening balance N+1), date-range sanity, sign convention. Failures block posting and show in an import report.
3.7 **Reconciliation.** Per account per statement period: statement closing balance vs ledger balance; a "reconciled" badge or a diff listing the unmatched rows. Internal transfer pairing (a card payment from checking pairs with the payment credit on the card) so spend isn't double-counted.
3.8 **Bank sync connector interface** (optional, BYO key): `Connector { listAccounts, fetchTransactions(since) }` with an adapter for SimpleFIN Bridge or the Plaid sandbox (see Decisions). Uploads stay the free default.

## M6 — Risk and analytics  (PRs 9–10)

6.1 `[spec]` **Anomaly detection with reason codes** (mirrors the Java `FraudEngine` style): `DUPLICATE_CHARGE` (same merchant + amount within 48h), `AMOUNT_OUTLIER` (robust z-score from median/MAD per merchant, above 3.5), `NEW_MERCHANT_LARGE`, `FEE_OR_INTEREST`, `SUBSCRIPTION_PRICE_CHANGE`, `FOREIGN_TXN`. Each alert carries its evidence. Alerts inbox with dismiss / confirm. DONE WHEN: a unit test per rule, including no-alert cases, and a measured false-positive rate on the user's own history recorded in the docs.
6.2 `[spec]` **Probabilistic cash-flow forecast.** Known items (recurring streams, paychecks) are placed on the calendar; discretionary spend is simulated by block-bootstrap of daily spend from the last 90 days, 2,000 paths, giving P10/P50/P90 balance to the next paycheck plus `P(balance < threshold)`. Seeded RNG for tests. DONE WHEN: tests on synthetic data with a known answer; a backtest script reports MAPE of P50 and the P10–P90 coverage rate, published in the docs.
6.3 **OLTP/OLAP split.** Ledger outbox events → S3 as Parquet partitioned by `user/yyyy-mm` (worker or Lambda) → DuckDB for heavy analytics (cohort-style month-over-month, merchant concentration). Postgres stays the source of truth; analytics can be rebuilt from events. Documented with a diagram.
6.4 **Reports.** Monthly close (reconciled / unreconciled, uncategorized count), cash flow statement, net worth over time (assets − liabilities from ledger accounts), budget vs actual by category. CSV export.

## Decisions (2026-11-10: plan approved; recommendations 1–4 accepted as defaults, item 5 still pending)
1. **Ingestion worker language:** Python (reuses `convert_bofa_pdf.py`, adds pandas/DuckDB skills for data roles, third runtime to maintain) **vs** Node/TypeScript (one less language; PDF parsing needs a new dependency). Recommendation: Python.
2. **Cloud split:** AWS for the pipeline (S3, SQS, Lambda, KMS; Terraform already exists) and nothing on Azure, **vs** adding one Azure piece (Key Vault for the KEK, cheaper than KMS's $1/month per key). Recommendation: AWS only; mention Azure equivalents in the ADR. Cost flag: one KMS key ≈ $1/month; everything else fits the free tier at ~10 users.
3. **Bank sync:** uploads only (free) **vs** SimpleFIN Bridge (~$15/year, user pays) **vs** Plaid (sandbox is free; real accounts need production approval). Recommendation: uploads first, connector interface ready, SimpleFIN later if wanted.
4. **Gamification:** remove completely, or keep an off-by-default "streaks" toggle. Recommendation: remove.
